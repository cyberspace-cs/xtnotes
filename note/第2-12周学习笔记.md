## 第 2 周：上下文工程与记忆系统

### 2.1 核心概念

**上下文工程**是 Agent 推理降本的第一杠杆——不是把对话全塞进 prompt，而是**用预算控制 + 分层记忆**在有限 token 中注入最有效信息。

### 2.2 五段式上下文预算

来源：`shuati-coach/server/agent/inference.py` 的 `_build_context_budget()`

```
┌──────────────────────┐
│ ① 系统提示 (400字)    │  ← 稳定前缀 → KV Cache 复用
├──────────────────────┤
│ ② 长期画像 (300字)    │  ← 稳定前缀 → KV Cache 复用
├──────────────────────┤
│ ③ 知识上下文 (500字)  │  ← RAG 动态注入
├──────────────────────┤
│ ④ 工具返回 (400字)    │  ← 上一次工具调用结果
├──────────────────────┤
│ ⑤ 对话历史 (600字)    │  ← 压缩后的滑动窗口
└──────────────────────┘
Total: ~2200 字（约 6000 token）
```

**核心设计原则**：
- **稳定前缀优先**：①② 在多轮对话中不变 → `prefix caching` 直接复用 KV，省掉 prefill
- **当前消息永不被裁**：用户最新输入 100% 保留
- **压缩算法**：TF-IDF 抽取摘要 → 保留 40% 关键信息，60% 冗余丢弃（40-60% 规则）

### 2.3 三层记忆系统

### 2.4 Context Rot 防御

| 问题 | 现象 | 项目防御 |
|------|------|---------|
| Instruction Fade-Out | 多轮后系统指令被淹没 | 稳定前缀（① 系统提示）每轮刷新 |
| Agent Drift | 行为偏离目标 | 反思节点每轮校验 + 技能注册表约束 |
| Context Compaction | 上下文过长无法处理 | 五段式预算 + TF-IDF 摘要 |

### 2.5 面试话术

> "我的记忆设计是**分层 + 预算制**：短期滑窗保对话连续性，长期画像存用户偏好，append-only 事件日志做审计追溯。五段式上下文预算中，系统提示和用户画像是稳定前缀，天然走 prefix caching，多轮对话不重算 prefill——这是工程上把 'context 压缩' 和 'KV cache 复用' 打通的例子。"

### 2.6 常见面试追问

- **Q：上下文超预算了怎么裁？** A：优先级裁剪——当前用户消息永不裁，其次保稳定前缀（身份/画像），最后压缩对话历史（TF-IDF 摘要）。
- **Q：为什么稳定前缀能省钱？** A：多轮对话中系统提示+画像不变，prefix caching 复用它们的 KV，第 2 轮起只做增量 prefill。
- **Q：分层记忆和 RAG 的区别？** A：记忆是「用户维度」的个性化历史，RAG 是「知识维度」的外部检索，二者互补——记忆决定"对谁说"，RAG 决定"说什么内容有依据"。

## 第 3-4 周：知识蒸馏（Knowledge Distillation）

### 3.1 核心原理

来源：`Audit-AIOPS/sft/distill.py`（GPU 版模板）+ `distill_compress.py`（numpy 可跑版）

```
                    ┌─────────┐
                    │ Teacher │  (大模型, 8192维特征)
                    │ acc=97% │
                    └────┬────┘
                         │ 软标签 (概率分布)
                         ▼
                    ┌─────────────┐
                    │  Distillation│  loss = α·CE_hard + (1-α)·T²·KL_soft
                    └──────┬──────┘
                           ▼
                    ┌─────────┐
                    │ Student │  (小模型, 512维特征)
                    │ acc=95% │  成本 ↓90%
                    └─────────┘
```

**Hinton 蒸馏公式**：
```
loss = α × CrossEntropy(y_hard, p_student)           # 硬标签损失
     + (1-α) × T² × KL(softmax(z_teacher/T), softmax(z_student/T))  # 软标签损失
```

- **温度 T**：T 越大，softmax 越平滑，暗知识（类别间相对关系）越明显
- **α**：硬标签与软标签的混合权重（半监督场景）

### 3.2 numpy 可跑版详解

来源：`Audit-AIOPS/sft/distill_compress.py`

```python
# Teacher: 大特征维度 (8192)，全量数据训练，能力强但体积大
Wt, bt = _train_softmax(Xtr_T, Ytr_oh, n_cls, epochs=80, lr=0.5)

# 关键：Teacher 在全部样本上打软标签——包含大量未标注样本
T = 3.0
teacher_soft = _softmax((Xtr_T @ Wt + bt) / T)

# Student: 小特征维度 (512)，标注预算仅 42 个样本
# (a) 只用硬标签 → 准确率低（数据不足）
Ws_hard, bs_hard = _train_softmax(Xtr_S[labeled_idx], Ytr_oh[labeled_idx], ...)

# (b) 蒸馏：硬标签(仅标注样本) + 软标签(全量样本)
#     把 Teacher 在未标注样本上的"暗知识"也利用起来
Ws_kd, bs_kd = _train_softmax(
    Xtr_S, Ytr_oh, n_cls, epochs=120, lr=0.5,
    soft_targets=teacher_soft, alpha=0.15, T=T,  # α 很小，因为标注样本少
)
```

### 3.3 半监督蒸馏的工程价值

真实业务中**人工标注昂贵**，只有少量带标签样本。蒸馏让 Student 能用 Teacher 在大量未标注样本上的软标签——**把未标注数据也用起来**。

模拟场景：
- 总样本 2000 条，人工标注预算仅 42 条（~2%）
- Teacher 不依赖人工标注（用全量数据训练）
- Student 通过 Teacher 软标签获取其余 98% 样本的信息

### 3.4 GPU 版蒸馏模板

来源：`Audit-AIOPS/sft/distill.py`

```python
# 真实场景：Teacher=Qwen2.5-72B → Student=Qwen2.5-1.5B
teacher = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-72B").eval()
student = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-1.5B")

def distill_loss(s_logits, t_logits, labels, temp=2.0, alpha=0.7):
    soft_s = F.log_softmax(s_logits / temp, dim=-1)
    soft_t = F.softmax(t_logits / temp, dim=-1).detach()
    kld = F.kl_div(soft_s, soft_t, reduction="batchmean") * (temp ** 2)  # 蒸馏损失
    ce = F.cross_entropy(s_logits.view(-1, s_logits.size(-1)), labels.view(-1))  # 任务损失
    return alpha * kld + (1 - alpha) * ce
```

| `distill_gain_vs_hard` | 蒸馏比纯硬标签的准确率提升 | 蒸馏有效性的直接证据 |

### 3.6 常见面试追问

- **Q：soft label 比 hard label 好在哪？** A：软标签是概率分布，含类别间相对关系（暗知识），比 one-hot 泛化更好。
- **Q：温度 T 的作用？** A：T 越大 softmax 越平滑，放大小概率类别的相对信息；蒸馏损失要乘 T² 补偿梯度缩放。
- **Q：蒸馏和微调（SFT）怎么选？** A：有 Teacher 且要小模型 → KD；无 Teacher 或任务窄 → SFT；可 KD+SFT 结合。
- **Q：为什么半监督蒸馏能省标注？** A：Teacher 在大量未标注样本上打软标签，Student 借此利用了 98% 的未标注数据。

## 第 5-6 周：量化与剪枝

### 5.1 INT8 对称量化

来源：`Audit-AIOPS/sft/distill_compress.py#L117-L127`

```python
def _quantize_int8(W):
    """fp32 权重 → int8（对称，per-column scale）"""
    scale = np.abs(W).max(axis=0) / 127.0   # 每列最大绝对值 / 127
    scale[scale == 0] = 1e-8
    q = np.clip(np.round(W / scale), -127, 127).astype(np.int8)
    return q, scale

def _dequant(q, scale):
    return q.astype(np.float32) * scale     # 推理时反量化回 fp32
```

**量化逻辑**：
```
fp32 值域 [-max, max]  ──scale──►  int8 值域 [-127, 127]
存储：4 bytes → 1 byte（4x 压缩）
推理：load int8 → dequant → matmul in fp32
```

**per-column scale**：每列独立计算 scale，比全局 scale 精度更高（每列的数值范围不同）。

### 5.2 幅度剪枝（Magnitude Pruning）

来源：`Audit-AIOPS/sft/prune.py`

```python
def _prune_by_magnitude(W, sparsity):
    """非结构化剪枝：|W| 最小的 sparsity 比例 → 置零"""
    flat = np.abs(W).ravel()
    k = int(len(flat) * sparsity)
    thresh = np.partition(flat, k)[k]       # 第 k 小的幅度作为阈值
    Wp = W.copy()
    Wp[np.abs(Wp) < thresh] = 0.0           # 低于阈值 → 0
    return Wp
```

**稀疏度扫描**（`prune.py` 主循环）：
```
sparsity:   0%    50%    70%    80%    90%    95%    98%    99%   99.9%
test_acc:  .974  .974   .974   .974   .970   .962   .958   .880   .642
nnz:       7168   3584   2150   1434    717    358    143     71      7
```

**关键洞察**：98% 稀疏（只剩 2% 权重非零）时精度几乎无损！

### 5.3 剪枝 + 量化 = 组合拳

剪枝和量化是**正交**的两条压缩路线：

| 技术 | 降什么 | 存储形态 |
|------|--------|---------|
| 量化 | 每个权重的比特数（32bit → 8bit → 4bit） | 密集 int8 |
| 剪枝 | 非零权重的个数（N → N×1%） | 稀疏 COO（值 + 索引） |

**工程正解**：先剪枝（降非零个数），再量化（降比特数），体积压缩可叠加。

```python
# 稀疏存储体积估算（COO 格式：每个非零 = 4B 值 + 4B 列索引）
def _sparse_bytes(W):
    nnz = np.count_nonzero(W)
    return nnz * (4 + 4)  # 非零数 × 8 bytes
```

### 5.4 GPTQ vs AWQ（面试必问）

| 方法 | 核心思想 | 优缺点 |
|------|---------|--------|
| **GPTQ** | Post-training 二阶信息补偿，逐列量化后用 Hessian 补偿未量化列 | 精度高，需校准集 |
| **AWQ** | 激活感知，保护 salient channels（激活大的通道少量化） | 实现简单，对 Transformer 友好 |

### 5.5 面试话术

> "我实际做过端到端的压缩流水线：蒸馏→剪枝→INT8 量化。98% 稀疏时精度不掉 1pt，叠加 INT8 量化后体积压缩超过 50×。核心思路是**先剪枝降非零个数、再量化降比特数**，两条正交路线叠加。验证策略是评测闭环——压缩后跑同一批测试集，准确率不掉即放行。"

### 5.6 常见面试追问

- **Q：per-channel 和 per-tensor 量化区别？** A：per-channel 每列独立 scale，精度高；per-tensor 全局一个 scale，简单但误差大。
- **Q：非结构化剪枝为什么实际加速有限？** A：稀疏分布不规则，通用 GPU 算子难利用；需稀疏算子或结构化剪枝（整行/整列/整头）才能实打实加速。
- **Q：量化后掉点怎么办？** A：① 用校准集做 GPTQ 二阶补偿 ② AWQ 保护 salient channels ③ 混合精度（关键层留 FP16）④ 评测闭环卡住掉点。

## 第 7-8 周：投机解码（Speculative Decoding）

### 7.1 核心原理

来源：`Audit-AIOPS/sft/speculative.py`

自回归解码的性能瓶颈：**每生成 1 个 token = 1 次大模型调用**

投机解码的核心思想：
```
不用等大模型逐 token 生成，让一个廉价 Draft 模型先"猜"k 个 token，
大模型做一次并行前向验证这 k 个——接受匹配的，纠正不匹配的。
```

### 7.2 算法流程

```
输入: prompt "我要申", Draft步长 k=4

第 1 轮:
  Draft 猜:   "请" → "制" → "作" → "U"
  Target 并行校验这 4 个:
    位置 0: Target 也预测 "请" → ✅ 接受
    位置 1: Target 也预测 "制" → ✅ 接受
    位置 2: Target 也预测 "作" → ✅ 接受
    位置 3: Target 预测 "Ukey的" (不是 "U") → ❌ 拒绝，采用 Target 结果
  产出: "请制作Ukey的" (3 个接受 + 1 个纠正)
  Target 调用: 1 次 (vs 纯自回归 4 次)

第 2 轮:
  当前序列: "我要申请制作Ukey的"
  Draft 猜:   "审" → "计" → "一" → "组"
  Target 校验: "审" ✅ "计" ✅ "一" ✅ "组" ✅
  产出: "审计一组"
  Target 调用: 1 次 (vs 纯自回归 4 次)
```

### 7.3 numpy 可跑版实现

```python
class NGram:
    """字符级 n-gram LM，模拟草稿/目标模型"""
    def __init__(self, order):
        self.order = order         # 1=bigram(草稿), 2=trigram(目标)
        self.table = defaultdict(Counter)

    def fit(self, texts):
        for t in texts:
            t = "^" * self.order + t + "$"
            for i in range(len(t) - self.order):
                ctx = t[i:i + self.order]
                nxt = t[i + self.order]
                self.table[ctx][nxt] += 1

    def next_char(self, ctx):
        ctx = ctx[-self.order:]
        c = self.table.get(ctx)
        return c.most_common(1)[0][0] if c else "$"
```

**投机解码验证函数**：
```python
def speculative(target, draft, prompt, n_new, k=4):
    while produced < n_new:
        # 1) Draft 连续提议 k 个字符
        proposals = [draft.next_char(draft_seq) for _ in range(k)]

        # 2) Target 一次并行校验
        target_calls += 1
        for d in proposals:
            t = target.next_char(cur)
            if t == d and t != "$":
                cur += d; accepted += 1    # 接受
            else:
                cur += t                   # 纠正
                break
    return output, target_calls, accepted
```

### 7.4 关键指标

```python
accept_rate = accepted / proposed      # 草稿接受率（越高越好）
speedup = ar_calls / sp_target_calls   # 加速比
```

**三个关键事实**：
1. **无损**：投机解码的输出分布与纯自回归完全一致（数学可证）
2. **接受率决定加速上限**：接受率 80% → 理论加速 ~5×，接受率 50% → ~2×
3. **Draft 质量和速度的权衡**：Draft 越大/越准，接受率越高；Draft 推理越快，每轮通信开销越小

### 7.5 面试话术

> "投机解码的核心是**用并行换串行**：让一个便宜的小模型猜 k 个 token，大模型一次并行前向验证。输出与纯自回归数学等价——是无损加速。接受率越高加速越大，草稿模型可以用蒸馏得到的小模型充当，形成一个闭环：蒸馏产出高效率 Draft，Draft 驱动投机解码加速推理。"

### 7.6 常见面试追问

- **Q：投机解码为什么是"无损"的？** A：Target 对每个位置做验证，只接受与 Target 自身预测一致的 token，不一致处用 Target 结果纠正，所以输出分布与纯 Target 解码完全一致。
- **Q：k（草稿步长）越大越好吗？** A：不是。k 太大，一旦前面某位拒绝，后面草稿全废；需根据接受率调优，通常 4-8。
- **Q：Draft 模型从哪来？** A：可用蒸馏小模型、同族小尺寸模型、或 n-gram/Medusa 头等。关键是又快又接近 Target。

## 第 9 周：企业级并行部署

### 9.1 四种并行范式

来源：`Audit-AIOPS/sft/parallel.py`

```
┌─────────────────────────────────────────────────────────────┐
│                      四种并行范式                              │
├───────────────┬───────────────┬───────────────┬──────────────┤
│  模型并行      │  流水线并行    │  上下文并行    │  组合显存     │
│ (Tensor MP)   │ (Pipeline PP) │ (Context CP)  │ (Memory)     │
├───────────────┼───────────────┼───────────────┼──────────────┤
│ 权重列切到N卡  │ 深度切成N段    │ KV沿序列切到N卡│ 量化×MP×CP   │
│ 解决单层太大   │ 解决空泡浪费   │ 解决长序列显存 │ 单卡显存总账  │
└───────────────┴───────────────┴───────────────┴──────────────┘
```

### 9.2 模型并行 / 张量并行

```python
def model_parallel(W, X, devices):
    """把权重矩阵的列均分到 N 张卡"""
    shards = np.array_split(W, devices, axis=1)   # 沿输出列切分
    partials = [X @ s for s in shards]            # 每卡算自己那段
    full = np.concatenate(partials, axis=1)       # All-Gather 拼接
    return full, shards
```

**正确性验证**：4/8 卡分片 → 输出与单卡逐元素一致 ✓

### 9.3 流水线并行

GPipe 利用率公式：
```
利用率 = microbatches / (microbatches + devices - 1)
```

示例（12 层模型，4 卡，16 个 micro-batch）：
```python
util_naive = 1 / 4 = 25%      # 朴素整批串行
util_1f1b  = 16 / 19 ≈ 84%   # 1F1B 流水 → 3.4× 利用率提升
```

### 9.4 上下文并行

长序列显存压力最大的是 KV Cache：

```python
def context_parallel(KV, devices):
    """把 KV 沿序列 T 切分到 N 卡，单卡只存 1/N"""
    chunks = np.array_split(KV, devices, axis=0)
    per_device_kv = (T // devices) * d  # 单卡 KV 显存降为 1/N
    return gathered, per_device_kv
```

### 9.5 组合显存预算

```python
def memory_budget(params, seq_len, kv_dim, devices_mp, devices_cp, bits_list):
    """单卡显存 = 权重(量化后/MP卡数) + KV(量化后/CP卡数)"""
    for bits in bits_list:
        per_device_weight = (params * bits / 8) / devices_mp
        per_device_kv     = (seq_len * kv_dim * bits / 8) / devices_cp
        total = per_device_weight + per_device_kv
```

以 7B 模型为例（4 张 MP 卡 × 4 张 CP 卡）：

| 量化精度 | 单卡权重 | 单卡 KV | 单卡总计 |
|---------|---------|--------|---------|
| FP32 (32bit) | 7.0 GB | 4.0 GB | **11.0 GB** |
| INT8 | 1.75 GB | 1.0 GB | **2.75 GB** |
| INT4 | 0.88 GB | 0.5 GB | **1.38 GB** |

### 9.6 核心原则：先压缩、再并行

```
Step 1: 蒸馏 → 学生模型（体积降 20-50×）
Step 2: 剪枝 → 稀疏权重（乘加削减 50×）
Step 3: 量化 → INT8/INT4（体积再降 2-4×）
Step 4: 并行 → 多卡部署（吞吐线性扩展）
```

**为什么不先并行再压缩？** 并行解决的是单卡放不下的问题，但成本跟卡数线性增长。先压缩可以**用更少的卡服务同样的模型**，或者**同样的卡服务更多并发**。

### 9.7 面试话术

> "企业部署模型的核心原则是**先压缩、再并行**。我实际做过蒸馏→剪枝→INT8 量化的压缩流水线，输出体积压 50×+、精度保持 95%+。在这基础上，模型并行解决单层太大、流水线并行解决空泡问题、上下文并行解决长序列 KV 显存爆炸。7B 模型经过 INT4 量化 + 4×4 并行后，单卡仅需 1.4GB——可以跑在消费级显卡甚至 CPU 上。"

### 9.8 常见面试追问

- **Q：模型并行和数据并行区别？** A：数据并行是每卡完整模型、切分 batch；模型并行是每卡部分权重、处理同一 batch。数据并行解决"训得快"，模型并行解决"放得下"。
- **Q：流水线并行的 bubble（空泡）怎么减少？** A：增加 micro-batch 数、用 1F1B 调度让前向反向交错，利用率从 1/N 提到 m/(m+N-1)。
- **Q：张量并行和流水线并行怎么配合？** A：张量并行在节点内（NVLink 高带宽），流水线并行跨节点（通信少），二者常与数据并行组成 3D 并行。

### 10.4 三个踩坑故事（面试必问）

**坑 1（编排引擎终点语义）**：
> `invoke` 在循环顶部判断 `if cur==finish: break`，导致 finish 节点（reflect）未执行即退出，反思建议全丢。修复为「先执行节点、再判断终点」——体现对「进入即停 vs 执行后停」语义的敏感。

**坑 2（幻觉误判口径）**：
> 初版把「拒答」样本（source="rag"，未作答的正确防幻觉行为）错算成幻觉，导致 hallucination_rate 虚高。修正为仅统计「声称作答却不相关」——体现评测指标口径必须与系统真实行为语义严格对齐。

**坑 3（防幻觉相关判据）**：
> 纯 TF-IDF 相似度会因常见字虚高误判相关。改为「相关判据仅依赖中文 2-gram 关键词真实命中」，TF-IDF 仅用于排序——体现 RAG 相关性阈值设计不能只看向量距离。
